# Architecture notes

This document explains the design decisions behind `infinitensor_test` for
anyone who wants to extend or modify it.

## Goals

1. **Reproducible.** Fixed seeds, persisted catalog, deterministic runs.
2. **Modular.** Pick a source, a check, a filter, independently.
3. **Engine isolation.** Only `TestEngine` imports InfiniTensor; the
   rest can be developed and unit-tested without it.
4. **PR-friendly.** A single command produces a markdown comparison
   suitable for pasting into a PR description.

## Components

### `config.py`

A simple dataclass `Settings` with three layers of overrides:
1. Default values (in code)
2. `config.local.yaml` (gitignored)
3. `ITEST_*` env vars
4. CLI args

This is the *only* place paths and environment knobs are stored. Tests
and CLI tools all read from `get_settings()`.

### `models/spec.py`

`ModelSpec` is the in-memory representation of "I want to test this
model". Key fields:

- `name` — stable identifier; used in result files
- `source` — which source produced the spec (torchvision, timm, synthetic, ...)
- `category` — high-level bucket for filtering/reporting
- `factory` — callable that returns the model
- `input_shape` — the shape to use at run time
- `tags` — free-form strings for filtering (e.g. "small", "transformer")
- `path` — filled in by the collector after materialization
- `size_hint_bytes` — used for early filtering

A spec may *also* be `skipped` if materialization fails (with `skip_reason`).

### `models/registry.py`

A dictionary of registered source functions. The `@register_source(id)`
decorator makes a function discoverable. This is the **plugin system**.

### `models/collector.py`

Given a catalog of specs, materialize them to disk. Idempotent: if a file
already exists and is under the size cap, it's reused. Supports `force`
to re-export.

The collector returns a stats dict: `{added, skipped, failed, elapsed_s}`.

### `runner/engine.py`

The core loop. For each spec:

1. **Load**: parse the ONNX file
2. **Compile**: build an `OnnxStub` (this is where InfiniTensor is exercised)
3. **Run**: copy a random input, call `stub.run()`, copy output
4. **Validate**: optional comparison to onnxruntime

Each step is wrapped in try/except, and the result captures:
- timing (load, compile, run)
- shape/dtype
- error type and message
- correctness (max abs/rel diff, cosine similarity)

The engine also aggregates results into a `RunSummary` (status counts,
latency percentiles, op coverage, correctness stats).

### `report/`

- `markdown_report.py` — self-contained markdown
- `html_report.py` — self-contained HTML (no JS)
- `comparator.py` — diff two result files, list newly passing/failing models

## Why so much emphasis on "models aren't committed"?

The .onnx files for the full 2,000-model suite weigh > 10 GB. They
also get out of date quickly as new models are added. The design here:

- **Source functions are committed** — they describe *how* to make a model
- **Generated .onnx files are not committed** — they're regenerated on demand
- The 1 TB data disk has plenty of room
- The catalog index (`catalog.json`) is also not committed; it's a build
  artifact, regenerated by `infinitensor-test-collect`

This means:

- A new contributor can clone the repo and run tests without downloading
  any pretrained weights
- The repo stays small (< 1 MB)
- A new model source is reviewed as a 30-line file, not as a 50 MB binary

## Why a CLI + pytest?

Both serve different users:

- The **CLI** (`infinitensor-test-run`, etc.) is for power users and
  CI scripts. It's scriptable, composable, and has no pytest dependency.
- **pytest** is for IDE integration, parametrized tests, and the familiar
  red/green workflow.

The same `TestEngine` powers both — pytest just calls `engine.run_one()`
in a loop with different filters.

## Where to add things

| If you want to...                            | Edit                                          |
|----------------------------------------------|-----------------------------------------------|
| Add a new model source                       | `src/infinitensor_test/models/sources/<name>.py` |
| Add a new test type                          | `tests/<category>/test_<name>.py`             |
| Add a new CLI command                        | `src/infinitensor_test/scripts/<name>.py`     |
| Add a new report format                      | `src/infinitensor_test/report/<name>.py`      |
| Change default behavior                      | `src/infinitensor_test/config.py`             |
| Tweak the synthetic op coverage              | `src/infinitensor_test/models/sources/synthetic_source.py` |
| Add a new suite                              | `src/infinitensor_test/utils/suites.py`       |

## Known limitations

1. **No parallel test execution.** Pytest-xdist would be useful, but
   InfiniTensor doesn't play well with multiple processes touching the
   GPU. Stick to sequential.
2. **No onnxruntime GPU path.** The reference runtime is CPU only. For
   larger models this is a 10-100x speed difference, but it's the
   simplest way to be correct.
3. **No native data download caching for the zoo.** Each run re-downloads
   if you clear the cache. We could improve this with `~/.cache/...`.
